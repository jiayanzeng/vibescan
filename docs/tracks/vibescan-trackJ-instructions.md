## Task J5 — Pin the classification-coverage ceiling with a named-Unknown assertion

### Spec basis
Architecture §14 (precision/recall harness, coverage metric). §6.2 (location
classification). §17.9 (the resolved `src/api/` question and its evidence
mechanism).

### Problem statement
`classification_coverage` is `0.7777…` — 7 of 9 eligible findings carry at
least one non-`Unknown` location. The number is recorded but nothing says
*which* two are unclassified or *why*, so it reads as a gap to close. By
inspection of the fixture set, the two unclassified findings appear to be
`src/history.ts` (`history-only-elevated-key`) and
`packages/nested/ignored-but-scanned/secret.ts` (`nested-gitignore`) — paths
carrying no framework signal, in fixtures that exist to exercise commit
provenance and gitignore layering, not classification.

If that is right, **7/9 is this corpus's ceiling, not a defect**, and the metric
currently cannot distinguish "the ceiling" from "a new classification
regression." A third `Unknown` would move the number without failing anything.

**Do not take the two names above on faith.** Derive them from the harness.

### Decision recorded here
Do **not** change the coverage denominator. Excluding
classification-irrelevant fixtures would make the number incomparable with
every historical value and would mask genuine `Unknown` regressions. Instead,
convert the ceiling into an asserted invariant.

### File targets
- `crates/vibescan-core/tests/precision_recall.rs`
- `STATE.md` (one line under the coverage record)

### Implementation guidance
1. Derive the exact set of eligible findings whose every location is
   `LocationClass::Unknown`, keyed by fixture name plus stable identity.
2. If the derived set is not exactly the two named above, **stop and report**
   — the discrepancy is more informative than the test.
3. Add a test asserting that set exactly: not a count, an equality on the named
   set. Include a comment stating why each member is expected to be
   unclassified, so the next reader sees a rationale rather than a magic
   number.
4. Add one line to `STATE.md` recording that `7/9` is the corpus ceiling, which
   two findings constitute the remainder, and that the set is now pinned.

### Acceptance criteria (self-verifiable)
1. The new test passes in default, `network`, `registry`, and
   `network,registry` graphs.
2. The asserted set is expressed as an exact equality; a test that only checks
   `len() == 2` does not satisfy this criterion.
3. **Negative control (regression direction):** temporarily add a third
   fixture path that classifies `Unknown`, or stub one classified location to
   `Unknown`; the new test fails and names the unexpected member. Revert and
   prove no residual diff.
4. **Negative control (improvement direction):** temporarily make one of the
   two expected members classify non-`Unknown`; the test fails, forcing an
   intentional baseline update rather than silent drift. Revert.
5. `corpus-metrics-baseline.json` is unchanged by this task.

## Task J6 — `scripts/check-status-consistency.py` + CI gate

### Spec basis
Root `AGENTS.md`, "Definition of done and status reporting." `scripts/AGENTS.md`
(verification-script contract: repo-relative discovery, `set -euo pipefail`,
offline-safe default, no real secrets, distinguish a smoke helper from the full
closeout matrix).

### Problem statement
Status drift has now been caught twice by audit and zero times by CI: Task CF2
(stale Track F worktree metadata) and this track's J1 (0.1.3 / license). The
existing remedy is a human review pass, which is precisely the control that
failed both times. Make it mechanical.

### File targets
- New: `scripts/check-status-consistency.py`
- `.github/workflows/ci.yml` (one new job)
- `scripts/AGENTS.md` (one paragraph describing the new checker's contract)

### Implementation guidance
Write a deterministic, offline, dependency-free Python checker that parses the
J1 `# vibescan:current-state` block and verifies each field against its source
artifact. Required checks:

1. `workspace_version` equals the version in every workspace crate manifest and
   in every `npm/**/package.json` — one mismatch fails.
2. `license` equals the workspace `license` field and the `license` field of
   every npm package.
3. `corpus_version`, `corpus_tp/fp/fn`, `corpus_precision`, `corpus_recall`,
   `classification_coverage` byte-match
   `tests/fixtures/corpus-metrics-baseline.json`.
4. `head_commit` resolves (`git cat-file -e`) and is an ancestor of `HEAD`.
   Skip this check with a clear message when git metadata is unavailable
   (shallow CI checkout); do not fail on absence.
5. No current-status document (`STATE.md`, `vibescan-architecture.md`,
   `README.md`, `FAQ.md`) contains a banned stale term. Seed the ban list with
   `routes/` as a classifier-rule reference. `docs/STATE-HISTORY.md` is
   exempt — it is the archive.
6. `integration_status` is one of the three permitted tokens.

Requirements:

- Reuse existing verification logic rather than duplicating it. Check
  `npm/scripts/verify-packages.mjs` first: if it already asserts npm/cargo
  version parity, call it or cite it instead of reimplementing, and say so in
  the file header.
- Repo-relative discovery; never embed an absolute path.
- Ship a `--self-test` mode with synthetic in-memory fixtures covering each
  check's pass and fail direction, matching the pattern in
  `check-network-boundary.py`.
- Exit 0 on success, 1 on a detected drift with a precise field-level message,
  2 on usage error.

Add a CI job `status-consistency` that runs `--self-test` and then the real
check.

### Acceptance criteria (self-verifiable)
1. `python3 scripts/check-status-consistency.py --self-test` passes.
2. The real check passes on the current checkout.
3. **Negative control, one per check:** for each of checks 1–3, 5, and 6,
   temporarily introduce the corresponding drift, confirm the checker exits 1
   and names the exact field and both values, then revert and prove a clean
   `git diff`.
4. The checker performs no network access and reads no file outside the
   repository. Prove it by running with no network.
5. The new CI job appears in `.github/workflows/ci.yml` and the file parses as

6. `scripts/AGENTS.md` describes the checker's contract, including that it is a

## Task J7 — CI: the fourth (`network,registry`) clippy and test graphs

### Spec basis

§13.1. Every instruction document from Tier F onward states acceptance
criteria over **all four** feature graphs.

### Problem statement
`.github/workflows/ci.yml` runs clippy and tests for `default`, `network`, and
`registry` — three graphs. The combined `network,registry` graph is compiled
and tested **only on the maintainer's machine**. `scripts/check-network-boundary.sh`
*does* build combined `cargo metadata` and the boundary checker validates
Supabase/Registry feature cross-activation, so the dependency policy is
covered — but nothing in CI proves the combined graph compiles clean or passes
its tests. That graph is exactly where feature cross-activation defects live,
and it is the one graph the project's own acceptance criteria demand that CI
does not run.

### File targets
- `.github/workflows/ci.yml`

### Implementation guidance
Add two jobs mirroring the existing ones exactly — same runner, same pinned
toolchain, same `--locked`:

- `clippy-all-features`: `cargo clippy --workspace --all-targets --features network,registry --locked -- -D warnings`
- `test-all-features`: `cargo test --workspace --features network,registry --locked`

Use `--features network,registry` explicitly rather than `--all-features`, so
that adding a future feature does not silently change what this job proves.
Keep job naming consistent with the existing `clippy-*` / `test-*` convention.

### Acceptance criteria (self-verifiable)
1. Both commands pass locally on the current checkout before the workflow is
   committed.
2. `ci.yml` parses as YAML and now contains four clippy jobs and four test jobs.
3. **Negative control:** temporarily introduce a warning reachable only under
   both features together (for example, an unused import behind

   `clippy-all-features` fails while `clippy-network` and `clippy-registry`
   pass. Revert and prove a clean `git diff`.
4. No existing job is modified.

## Task J8 — Workflow hardening: least-privilege permissions, action alignment, SHA pinning

### Spec basis
Architecture §13.1 (single static binary, five-target matrix, provenance).
Track G0.3's decision that the npm channel **ships rather than downloads** —
recorded there explicitly as a security invariant, not a style choice.

### Problem statement
The release path's own supply-chain posture is weaker than what the tool
enforces on its users:

- `.github/workflows/ci.yml` and `.github/workflows/verify-static-linux.yml`
  carry **no `permissions:` block**, so they inherit the repository default
  token scope. All six other workflows set one.
- `ci.yml` pins `actions/checkout@v4` while every other workflow uses `@v6`.
- **No action anywhere is pinned to a commit SHA** — including in
  `release.yml`, which holds `attestations: write` and `id-token: write`. A
  scanner that detects hallucinated dependencies and made "ships, not
  downloads" an invariant is signing provenance through mutable third-party
  tags.

### File targets
- `.github/workflows/ci.yml`, `verify-static-linux.yml`, `npm-smoke.yml`,
  `package-npm.yml`, `publish-all.yml`, `publish-crates.yml`, `publish-npm.yml`
- `.github/workflows/release.yml` — **only if J0 established it is not
  `dist`-generated**
- `dist-workspace.toml` — only if it exposes a supported action-pinning option

### Implementation guidance
**(a) Permissions.** Add `permissions: contents: read` at workflow level to
`ci.yml` and `verify-static-linux.yml`. Do not widen any existing permission
block. Publish jobs keep their escalated scopes.

**(b) Version alignment.** Raise `ci.yml`'s `actions/checkout` to the version
used by the rest of the repository. Do not upgrade any other action's major
version in this task — pinning and upgrading are separate risks.

**(c) SHA pinning.** For every third-party action, resolve the tag to its
